# Islands Architecture & Hydration

Deshijs ships zero client JavaScript by default. When interactivity is needed, you opt-in at the **usage site** using `client:*` directives.

## What are Islands?

In traditional single-page frameworks, adding one interactive widget (like an image carousel or a dark mode toggle) forces the entire page to ship a heavy JavaScript runtime.

Deshijs implements the **Islands Architecture**:
- Static HTML is generated on the server at build time.
- Only components carrying a `client:*` directive are bundled into browser JavaScript chunks (`/_deshi/c/<Component>.<hash>.js`).
- Pages without islands ship **0 bytes of client JS**.
- Every island is wrapped in a `<deshi-island>` element (the equivalent of Astro's `<astro-island>`) and hydrated by the same lifecycle mechanics as Astro: once-per-page prescripts, top-down hydration, Astro-format props and the `deshi:hydrate` / `deshi:unmount` events.

---

## The 5 Hydration Strategies

| Directive | Strategy | When It Hydrates |
| --- | --- | --- |
| `client:load` | Immediate | On initial page load. Emits `<link rel="modulepreload">` for instant fetching. |
| `client:visible` | Viewport Trigger | When component scrolls into the viewport via `IntersectionObserver`. |
| `client:idle` | Background Idle | When browser is idle via `requestIdleCallback` (with 200ms timeout fallback). |
| `client:media="(query)"` | Media Query | When CSS media query matches (e.g. `client:media="(max-width: 768px)"`). |
| `client:only` | Client Only | Skips SSR entirely and mounts directly in the browser. |
---

### 1. client:load (Immediate)
```html
<Navbar client:load />
```
Hydrates immediately as soon as the page loads. The build engine also injects a `<link rel="modulepreload">` tag into `<head>` to prioritize chunk downloading.

---

### 2. client:visible (Viewport Trigger)
```html
<ImageCarousel client:visible />
```
Hydrates only when the component enters the visible viewport. Matches Astro exactly: an
`IntersectionObserver` watches the island's **children** (the island element itself is
`display: contents` and never intersects) with an optional root margin:

```html
<ImageCarousel client:visible={{ rootMargin: '200px' }} />
```

---

### 3. client:idle (Background Idle)
```html
<NewsletterSignup client:idle />
```
Hydrates during idle time via `requestIdleCallback` — exactly like Astro, with no viewport
gate. Options are passed through:

```html
<NewsletterSignup client:idle={{ timeout: 500 }} />
```

`requestIdleCallback` runs with the given `timeout` (browsers without it fall back to
`setTimeout(200)`).

---

### 4. client:media (Media Query)
```html
<MobileMenu client:media="(max-width: 768px)" />
```
Hydrates only when the media query matches. Ideal for responsive navigation drawers that are not visible on desktop viewports.

---

### 5. client:only (Client Only)
```html
<CanvasGame client:only />
```
Skips server-side rendering entirely. Useful for browser-only libraries like Three.js, Canvas, or WebGL.

<Callout type="warning" title="client:only ships no HTML">
  Because SSR is skipped, a `client:only` component renders nothing until its
  JavaScript loads — never rely on it for content that must be in the initial
  HTML (SEO, above-the-fold text, or a no-JS fallback).
</Callout>

## Passing Props to Islands

Like Astro, any standard props passed to an island component are automatically serialized into the SSR HTML and made available during client hydration:

```html
<Counter initialCount={42} step={2} client:visible />
```

The compiler automatically serializes the props into the `props` attribute of the
`<deshi-island>` wrapper using Astro's typed-tuple format (`[type, payload]`), so `Date`,
`Map`, `Set`, `RegExp`, `BigInt`, `URL`, typed arrays, `Infinity` and `undefined` all survive.
During hydration they are revived and passed to the component's `<script client>` mount
function as `ctx.props`.

## Authoring Island Components (`<script client>`)

Declare browser interactivity within a `<script client>` block inside your component:

```html
<script>
  // Server-side prop defaults
  const start = props.start || 0;
</script>

<div class="counter">
  <button class="dec">-1</button>
  <span class="count">{start}</span>
  <button class="inc">+1</button>
</div>

<script client>
  // Browser island code: `root` is the component root DOM element
  const btnInc = root.querySelector('.inc');
  const btnDec = root.querySelector('.dec');
  const display = root.querySelector('.count');

  let count = ctx.props.start || 0;

  btnInc.addEventListener('click', () => {
    count++;
    display.textContent = count;
  });

  btnDec.addEventListener('click', () => {
    count--;
    display.textContent = count;
  });
</script>
```

## Multi-Framework Islands (React, Preact, Vue, Svelte)

Deshijs natively supports importing and hydrating UI framework components directly inside `.deshi` files, matching Astro's multi-framework islands:

```html
<script>
  import ReactCounter from './components/ReactCounter.jsx';
  import VueWidget from './components/VueWidget.vue';
  import SvelteButton from './components/SvelteButton.svelte';
</script>

<!-- Rendered statically at build time (0 bytes client JS) -->
<ReactCounter initial={10} />

<!-- Hydrated in the browser using the framework's client runtime -->
<ReactCounter initial={10} client:load />
<VueWidget title="Dashboard" client:visible />
<SvelteButton client:idle />
```

### How It Works:
- **Zero-Config Detection**: The compiler recognizes `.jsx`, `.tsx`, `.vue`, and `.svelte` files automatically.
- **Server Rendering (SSR)**: At build time, the component is rendered to static HTML using the framework's SSR renderer (`react-dom/server`, `@vue/server-renderer`, `svelte/server`, or `preact-render-to-string`).
- **Client Hydration**: When a `client:*` directive is attached, Deshijs wraps the SSR output in a
  `<deshi-island>` custom element (Astro's `<astro-island>` equivalent) and generates a
  self-contained island chunk (`/_deshi/c/<Component>.<hash>.js`) that mounts the component into
  the DOM. The chunk bundles the framework runtime so hooks and context work exactly as in Astro.
- **Props Passing**: Standard props are serialized into the island's `props` attribute
  automatically and passed to both the server renderer and client hydration.

## Runtime Internals (islands.ts)

In `packages/compiler/src/islands.ts`:
- `renderIsland(...)`: wraps the SSR output in `<deshi-island uid component-url component-export renderer-url props ssr client opts await-children>` — Astro's `<astro-island>` attribute contract, including the `<!--deshi:end-->` completion marker for streamed children.
- `islandPrescripts(state, strategy, dev)`: emits the once-per-page prescripts immediately before the first island — the `deshi-island,deshi-slot{display:contents}` style, the directive function (`(self.Deshi||(self.Deshi={})).load=…` plus a `deshi:load` event), and the `deshi-island` custom element definition. All classic scripts, like Astro; dev builds keep them readable, production minifies them.
- The `deshi-island` custom element loads `component-url` and `renderer-url` in parallel, hydrates **top-down** (a child waits for its parent island's `deshi:hydrate`), revives props, collects `deshi-slot` / `template[data-deshi-template]` slots, removes `ssr` when done, and fires `deshi:hydrate` / `deshi:unmount` / `deshi:hydration-error` events.

Props are serialized with Astro's typed-tuple encoding in `packages/compiler/src/serialize.ts` and revived on the client by the same module's `reviveProps` (inlined into the prescript via `toString()`).
